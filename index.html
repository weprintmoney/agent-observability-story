Arize PM take-home · an AX field test

Agent evals that work on day one

By Charlcye MitchellOct 8, 2026Free tier~9 min read
TL;DR

I built a real agent and ran it through Arize AX. The good news: tracing paid off in 60 seconds. The gap: a score I could trust took 25 minutes and three failures in a row. Here's what I built, what worked, where it broke, and what I'd build so the next developer reaches the "this works" moment in under five minutes.

1

What I built, and why

A docs-drift reviewer on Claude Opus 5.5.

  • The problem My agent pipelines treat per-folder CLAUDE.md files as the index for context navigation. When a PR merges and that index drifts from the repo, downstream agents silently miss documents. I used to check for this drift by hand.
  • The agent Given a merged PR, the agent reads the repo’s own doc rules, checks every added or renamed file against the nearest index, greps the index docs for stale paths, and submits structured findings. A deterministic verifier re-checks each finding and marks the root span ERROR if one does not hold up.
  • The data I built and tested it on 74 labeled PRs from two of my repos. The user, the failure cost, and the ground truth are all real: those repos carry an explicit “update the doc index” hook, so merge history was already a labeled dataset.

First traced batch: right on 26 of 31, plus 6 verified problems my labels had missed. Two of my first three "false positives" were label errors. The agent corrected my dataset three times.

2

The good: where AX shines

  1. Tracing worked on the first try. register(), the Anthropic auto-instrumentor, and my own AGENT, TOOL and CHAIN spans. Traces appeared in under a minute.
  2. The trace drawer is the best screen in the product. The whole agent in one tree, latency and tokens per step, the review summary readable in place. This screen made me trust the rest.
  3. Agent Graph got the topology right in one look. Start, the agent, six tool and LLM nodes, end. Sequence is flattened, so you can't see that get_pr always runs first; that lives in Agent Path.
  4. Dataset upload just worked. 70 rows as a list of dicts, mixed string and integer columns, first try. One gap: when the agent corrected a label, I couldn't find the example to update in place within the default page size of 50, so I shipped a v2 dataset (versioning is in the API, I just didn't reach it). There's also no one-click "this row's label is wrong" from the experiment view back into the dataset, which would have been useful.
  5. Experiments saved me from shipping a bad prompt. I wrote prompt v2 with two rules the first batch had missed, then ran v1 against v2 over all 70 labeled PRs as AX experiments: the agent as the task, five code evaluators, one LLM judge. v2 fixed the case it was written for and broke three others. Without the experiment I probably would have shipped the regression on one fixed example.
3

The friction: what needs fixing

Getting to an eval I trusted was the bumpy part. The five that matter, then the full list ranked by how much each would hurt a team on a trial.

1. Cost is a black box

  • The issue AX counted 687k input tokens and had the model name on every span. Cost read "--" everywhere: project header, Cost tab, Sessions, Experiments. Right next to an upsell for a cost-reduction agent.
  • The fix Price tokens at public list rates, label them as estimates, and let customers upgrade to accurate cost tracking. You can't reduce spend you can't see.

2. The first gate: Code Evaluators, and a hidden naming rule

  • The issue The first evals I wanted were deterministic: did it submit, did the findings verify, did it stay in budget. Code Evaluator is Enterprise-only, so I computed them locally and wrote them back with spans.update_evaluations. All 32 failed with “No matching span found.”
  • The cause A naming rule: dots are not allowed in eval names. That rule prints at INFO, above the errors. I spent ten minutes chasing span ids for a naming mistake.
  • The fix Make the naming rule a validation error, and fail the call when every eval column gets dropped. And put the cheapest, first evals a developer writes on every plan (more on that in the proposal).

3. The LLM judge builder failed three times in a row

The builder itself is clear and linear: type, name, scope, model, template with {variables}, then map to real columns with a live preview. Then “Test Evaluator On Spans”:

  1. Raw GraphQL error. “Classification choices are required.” Nothing in the form had asked for them. The Labels section sits below the template, below the fold, with no required marker.
  2. Provider error. The runner forces tool_choice, which Claude 5.5 models reject. The picker offers those models anyway. Eng note: an afternoon’s fix (don’t force tool choice on models that reject it, or hide them). A trial user just concludes evals are broken.
  3. The workaround, found by guessing. Advanced Options, “Enable Function Calling” off. Third test: GROUNDED in about 8 seconds. The model was fine the whole time.

4. The silent-failure experiment

  • The issue My first experiment ran out of API credits after 16 rows. The task returned the error string instead of raising. AX marked all 70 runs COMPLETED, and my evaluators scored 54 identical error strings as predictions.
  • Whose bug That bug was mine, and I fixed it: the task now raises, and evaluators skip failed rows. The experiment page still showed 70 green runs, with no hint that 54 outputs were the same string.
  • The fix One heuristic nudge: “54 of 70 outputs are identical. Do these look like errors?”

5. Prompt Playground: close, but two bugs in the loop

  • What it is It is a single-call prompt tool: dataset variables, optional function schemas, one model call per row. It cannot run my tool loop (the “agent endpoint” quickstart is the path for that), but it can compare judge prompts over the agent’s real outputs, which is what I tried.
  • The issue Column B’s model picker closed itself about a second after opening, six attempts running. Two datasets I had created through the SDK minutes earlier did not appear in the dropdown until a hard reload. The comparison ran from code instead.
  • Why it matters The code-to-UI loop the dev workflow depends on has a cache in it, and the A/B tool’s B column is hard to configure.

Every rough edge, ranked

1 = shrug. 5 = a team on a trial stops here. Scores were assigned as each item was logged, not later.

Where the high scores cluster is the finding. Tracing issues scored 2s and 3s. The path from "traces are flowing" to "a score I trust" scored 4s and 5s. Four of the top six sit on that path.

4

The aha: an agent judge has to see the trajectory

When the online judge finally ran, it scored 24 of 32 reviews GROUNDED and 8 UNGROUNDED. (The first backfill, in the screenshot, was 19 of 24 scored spans, which is the 79%.)

I read the 8 failures. Every one had the same shape. The agent’s summary stated something it had verified with a tool (“nothing was renamed or deleted”). The judge, which sees only attributes.output.value on the AGENT span, called it unsupported. The trace held the get_pr result that proved it. The judge never saw it.

The judge was right about its inputs and wrong about the agent.

I tested the fix instead of asserting it

I exported the 32 traces from AX and re-judged each one twice with Claude Sonnet 5.5: once on the output alone, once with the agent’s task, its rules, and its tool calls in order.

  • Without the trajectory A strict judge passed 2 of 32. AX’s lenient template had passed 24. The verdict tracked the prompt, not the agent.
  • With the trajectory 26 of 32. Five of the eight UNGROUNDED verdicts flipped to GROUNDED, each citing the tool result. Three reviews AX had passed were now flagged, each citing the line the summary contradicted. On my reading, all three flags are right.

5

What I'd build

Make the first useful eval on an agent project take under five minutes, with no provider key and no plan upgrade, and put the trajectory in front of the judge before the user has to ask.

The problem, plainly

Tracing proves its value on day one. Evals don't. Between "traces are flowing" and "a score I trust" are several hurdles.

  • The public record agrees Across 1,960 public developer posts I coded over six months, agent testing and eval authoring are the second and third largest themes outside GitHub. LangSmith and Braintrust put code evaluators on their free tiers.
  • It gets more urgent Providers now publish a minimum model life of about 12 months, and by my count 21 text-model shutdowns are scheduled between Oct 20 and Dec 11, 2026. Every agent gets re-qualified on a new model at least once a year. Evals are the regression suite for that day. And Dynatrace and Datadog management both name token overruns as the customer fear, which is why a dollar figure on every trace is table stakes.

A · AGENT HEALTH PACK
Free, deterministic, offered automatically

  • The MVP On agent projects, Add Eval offers six built-in checks that need no model and no provider key: completed, tool_budget, tool_loop, truncated_output, error_in_trace, latency_outlier. Pure functions over attributes the instrumentors already emit. Exactly what I wrote by hand on day one. Free on every plan.
  • Detect agents by shape, not label A root span with a TOOL descendant and more than one LLM descendant. Most instrumentors label the orchestrator CHAIN, not AGENT, so keying on span kind would miss most LangGraph and ADK agents.

B · TRAJECTORY FIRST
Offer the judge what the agent saw

  • The MVP From an agent project, lead with trace scope and a {trajectory} variable: tool calls in order, with arguments, truncated results and status.
  • Offered, not defaulted It waits for trace completion and costs several times the tokens on the customer's key, so the estimate is shown first.

C · PRE-FLIGHT
Run it on three real spans before Save

  • The MVP Validate required fields inline. Translate provider errors into plain language with the fix attached. Stop forcing tool choice on models that reject it.
  • Quick win alongside A default price table, so Cost stops reading "--."

Nothing new in the data path

The detector is a shape query. The pack reads existing attributes. The digest is a rendering policy. Results land as ordinary eval columns, so Signal, monitors and Alyx see them unchanged. One new output: each verdict can also go out as a webhook event, ready for the parent platform's workflows.

How I'd take it to engineering

  1. Three repros first, independent of the bet. Forced tool_choice on 5.5 models, the dot-in-eval-name error that blames span matching, and the Cost tab setting a range the plan can't serve. Small changes, clear tests, and each removes a moment where a trial ends.
  2. Pre-flight, one sprint. Reuses the existing "Test Evaluator On Spans" call. What changes: the order (pre-flight before Save), client-side validation, and a table mapping errors to fixes.
  3. The pack, two sprints. Six pure functions, one UI card. The eval-column plumbing exists. The detector can run lazily when Add Eval opens before we commit to running it on ingest.
  4. Trajectory last. It touches template variable resolution, trace-completion timing and the Add Eval entry point. Two questions for the team before designing it: how does the online pipeline decide a trace is complete, and what's the median judge input size today?
  5. Plan gating is a funnel argument. Deterministic checks are what keep people around long enough to buy judges, Signal and seats. Gating them gates the funnel.

Who else is here

No competitor I checked offers a free, prebuilt, no-LLM health pack for agents. Grafana's Agent Observability, GA since July, already scores multi-step turns and whole conversations with LLM judges, so trajectory-aware judging alone isn't a moat. What would set AX apart is the combination: free deterministic checks every agent gets on day one, trajectory-aware judging, and verdicts that flow into the parent platform's workflows.

Grafana evaluation docs · GA note

What I'm not proposing

A new eval DSL. A replacement for Code Evaluators on Enterprise, which stay the path for custom checks. Changes to Signal or Alyx. The pack is deliberately boring: six checks that hold for every tool-using agent.

Limits of this evidence

One user, one free-tier account, one agent, one week. The judge findings come from 32 spans. The voice-of-customer data is public discussion and over-represents developers who post (81% GitHub; enterprise buyers barely appear). What it does support is the shape of the on-ramp problem and the specific failures, each of which I can reproduce.

Artifacts, method, and where Claude Code helped

Artifacts

  • The agent About 400 lines of Python: five gh-backed tools, the tool-use loop, the deterministic verifier, and the OpenInference tracing. Prompt v1 and v2.
  • Dataset and experiments 74 labeled PRs with evidence and hand overrides, 70 uploaded to AX as two dataset versions. The experiment runner with five code evaluators and one LLM judge. The free-tier script that logs code evals back onto spans.
  • Trajectory re-judge The 32 traces exported from AX and the script that judged each one with and without the trajectory. The explorer above is built from its output.
  • Dated findings log Every rough edge in the order it happened, with hurt scores assigned at the time. Thirteen screenshots, eleven of them on this page.
  • AX project docs-drift-reviewer: traces, the online judge, two datasets, the v1 and v2 experiments.

Code, data and the log are available on request.

Method

Everything above was done on a free-tier AX account between Oct 3 and Oct 7, 2026. Hurt scores were assigned when each item was logged, not later. The voice-of-customer figure comes from a six-month coding of public developer discussion I ran before the take-home. Model-shutdown counts come from provider deprecation pages as of October 2026.

Where Claude Code helped, and where it didn't

  • Helped most Work with a clear spec: the deterministic verifier, the dataset labeler, the experiment harness, and moving the experiments to a different runtime when my API credits ran out. I also had it drive the AX UI while I watched, which is how the three judge-builder failures were captured with screenshots in the order they happened.
  • Helped least The SDK's newer surfaces. The docs it knew were stale, so it introspected function signatures, and the eval-naming rule isn't documented anywhere a model would think to look.
  • Mine The use case, the hurt scores, what to cut, and the proposal. I read every judge explanation and every experiment row myself. Any mistakes here are mine too.
