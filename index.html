AI observability · 2015 → 2031

The Trajectory

For ten years, monitoring AI meant watching what a model predicted. Agents changed the question. Now we have to watch what a system did, step by step, and decide whether we trust it.

By Charlcye MitchellOctober 2026~18 min read
Scroll. The figures change as you read.

This piece has three parts. The first is a short history of how the field learned to watch machine learning in production, told through the question each era asked. The second is a set of dated predictions about where it goes next, each graded by how much evidence stands behind it. The third is a field test: I built a working agent, put it on Arize AX, and wrote down every place the product helped and every place it got in the way. It ends with what I would build.

The history and the field test lead to the same conclusion. The unit of observation keeps getting bigger. It went from a prediction, to a completion, to a trajectory. Each time it grew, the tools for judging it lagged behind the tools for recording it.

Chapter I

Has the input changed?

2015 – 2021 · the model era

Monitoring began as a statistics problem. A model was a function, and the worry was that the world would drift away from the data it learned on.

NIPS · 2015

The model is the small box

In 2015, Google researchers drew ML code as a small black box inside a much larger system: data collection, serving, configuration, monitoring.

The paper is about technical debt. The industry's takeaway was narrower: production failures usually happen around the model, and someone has to watch for them.

Sculley et al., NIPS 2015
The core question

Is production still the training data?

A fraud or credit model returns a number. The truth arrives weeks later, when the transaction clears or the loan defaults. So teams watched for the conditions that make a model wrong instead.

Drift

When inputs move away from the training data, the model is extrapolating. Model-era monitoring compared this week's feature distributions with a baseline and alerted when a statistic like PSI crossed a threshold.

A narrow and well-defined problem

Tabular inputs, numeric outputs, settled math. Vendors competed on three hard parts: scale, joining delayed ground truth back to predictions, and explaining which feature moved.

2018 – 2020

A category forms

Fiddler and Arthur (both 2018) led with explainability for regulated buyers. Arize emerged in 2020 focused on production performance. WhyLabs spun out of AI2 that September; Evidently open-sourced a drift report in November.

All of them observed the same unit: a prediction.

Foundation Capital on Arize · WhyLabs launch · Evidently on PyPI · Fiddler and Arthur dates from press coverage
Chapter II

What did the model say?

2022 – 2024 · the prompt era

Then the output became language, and the statistics stopped working.

2022-11-30

The output is a sentence

After ChatGPT, every product team shipped on an LLM. A drift statistic can't tell you whether a sentence is true. The failure that mattered was a fluent, confident wrong answer, and it doesn't show up in a distribution.

Tracing comes back

The field borrowed tracing from distributed systems. Retrieve, prompt, call, parse: each step became a span with inputs, outputs, latency and tokens. When an answer was wrong, the trace often showed why.

Models grading models

With no fast ground truth, teams used a second model as the grader. LLM-as-a-judge made it cheap to score every trace, with an explanation attached.

It also introduced the failure mode the rest of this story turns on: a judge is only as good as what it is shown.

2023 – 2024

A second wave, and a standards fight

Phoenix (April 2023), then LangSmith, Langfuse and Braintrust that summer. Arize published OpenInference; OpenTelemetry merged GenAI conventions in 2024 that are still marked "development." Datadog shipped LLM Observability in June 2024. The incumbents had arrived.

LangSmith · Langfuse · OpenInference · OTel #825 · Datadog · MCP
Chapter III

What did the agent do?

2025 – 2026 · the agent era

An agent decides its own next step, so the trace is no longer a fixed pipeline. It's a record of decisions.

2025

Frameworks ship with tracing built in

OpenAI's Agents SDK (March 2025) shipped with tracing on by default. Google's ADK followed in April, Anthropic's Claude Agent SDK in September. The agent loop, and a basic trace of it, became a commodity.

OpenAI · Google ADK · Claude Agent SDK

The questions change shape

Did it finish? Did it loop? Did it stop because it was done, or because it ran out of tokens? These are questions about the trajectory, the path the agent took, not about any one model call.

Most don't need a model to answer. They're properties of the span tree.

The judge's blind spot

Most evaluation still reads only the final answer. If the agent says "nothing was renamed," a judge that sees only that sentence can't know the agent checked. In chapter VI this happens to me on 1 verdict in 4.

2025 – 2026

The reader is a model too

Since MCP, observability platforms expose traces to coding agents. A developer can ask an IDE assistant why last night's runs slowed down, and it answers from the traces. In public developer discussion, this is one of the most-praised features.

Chapter IV

The category gets bought

2025 – 2026 · consolidation

In eighteen months, most of the independent companies in this story were acquired by larger ones, folded into them, or shut down.

The map at the start of 2025

A dozen credible AI-native vendors, most venture-backed and growing. Weights & Biases went to CoreWeave in May 2025; Anthropic hired Humanloop's team in August. Neither was a pure observability deal. Both pointed the same way.

Signed in August, closed October 1: about $815M in cash plus replacement equity. Phoenix and AX continue. The pitch is one platform that watches both a bank's infrastructure and the agents running on it.

The rest of the board

ClickHouse bought Langfuse in January, and Langfuse stays open source. WhyLabs shut down and open-sourced its platform. Mintlify absorbed Helicone in March. In February, Gartner named the market: AI Evaluation and Observability Platforms.

ClickHouse · WhyLabs · Mintlify · Gartner

What consolidation means

AI observability is becoming a module of a broader platform, as application monitoring did a decade ago. The AI-native depth is no longer the whole product. It's why a developer adopts the platform before anyone buys it.

Chapter V

What comes next

2027 – 2031 · predictions, graded

Forecasts are cheap. Below are six, each with a date, the mechanism behind it, and how confident the evidence lets me be.

These come from a longer forecast I wrote this month. It covers seven facets (hardware, models, agent architecture, protocols, enterprise operations, skills and buyer economics) and produced 28 prediction cards. After a separate adversarial review, four held at High confidence on narrowed claims. High means two or more independent measured sources or a dated binding obligation. Medium means one measured source plus corroboration. Low means mostly vendor or analyst claims. Vendor claims alone never raise a prediction above Medium.

High  in motion

Every agent will be re-qualified on a new model at least once a year

Providers now publish a minimum model life of about 12 months and 2 to 6 months' notice. By my count, 21 text-model shutdowns are scheduled between October 20 and December 11, 2026.

So: evals become a regression suite, needed most on the day a model disappears.

High  now → 2029

Cost per run becomes the first number anyone looks at

Dynatrace and Datadog management both cite token overruns as the customer fear. Vendors bill in at least three units, none of them tokens, and list prices for the same workload vary about 9x.

So: a dollar figure on every trace is table stakes.

Medium  through 2028

The standards won't settle soon

The OpenTelemetry GenAI namespace is still at development status, with no dated plan to stabilize it. OpenInference and vendor dialects likely stay above 30% of agent telemetry through 2028.

So: ingest, and every check that reads spans, has to handle several dialects.

open-telemetry/semantic-conventions-genai
High  2027-12-02

Logs become evidence

EU AI Act Article 26(6) requires deployers of high-risk systems to keep logs for at least six months. For Annex III systems that applies from 2 December 2027.

So: retention is the easy part. Whether examiners will ask for verdicts as well as traces is the bet.

Art. 26 · Reg. (EU) 2026/1744
High / Medium  2029

No "agent operations" job is forming, so AI engineers and SREs share the pager

Job postings show no new title for whoever runs agents in production (High). Who carries the pager is unmeasured. Dynatrace names AI engineers, SREs and platform teams together (Medium).

So: one signal, two readers: the developer's IDE and the SRE's on-call tooling.

My bet  2029 – 2031

Cheap, deterministic verdicts become the trigger for control

Something will stop a misbehaving agent mid-run. It needs a trigger that is fast and cheap and doesn't depend on another model's opinion: a loop, a blown budget, an error in the trace.

So: the humble checks are the strategic ones, and exactly what I couldn't get on day one.

Each era's tools recorded the new unit of observation well before they could judge it. Agents are where that gap is widest today.

Chapter VI

I put a real agent on Arize AX

October 2026 · free tier · one week

To test the thesis, I built an agent I actually needed, instrumented it, and ran both of AX's core workflows on it.

What I built

A docs-drift reviewer

My agent pipelines use per-folder CLAUDE.md files as their map. When an index drifts, downstream agents silently miss documents. I used to check every merge by hand.

Given a merged PR, my agent checks new and renamed files against the repo's own index rules, then a deterministic verifier re-checks each finding.

Why this use case

It has a real user (me), a real failure cost and real ground truth: my repos have an explicit index rule, so merge history is a labeled dataset. I labeled 74 PRs; 70 went into AX.

First batch: right on 26 of 31, plus 6 verified problems my labels missed.

Observability workflow

Tracing worked first try

The auto-instrumentor plus my own AGENT, TOOL and CHAIN spans, and traces appeared within a minute. The trace drawer is the best screen in the product: the whole agent in one tree, with latency and tokens per step.

Agent Graph got the shape right

One look shows which tools the agent uses. It flattens the order, though: you can't see that get_pr always runs first and submit_review last. Order lives in Agent Path.

Tokens counted, dollars missing

AX counted 687k input tokens, with the model name on every span. Cost still read "--" everywhere, next to an upsell for a cost-reduction agent. You can't reduce spend you can't see.

The first gate

The first evals I wanted were deterministic: did it submit, did findings verify, did it stay in budget. Code Evaluator is Enterprise-only, so I computed them locally and wrote them back through the SDK.

All 32 failed with "No matching span found." The real cause: dots aren't allowed in eval names.

An LLM judge, built in the UI

Next, a judge: is the summary grounded in the findings? The builder is clear and linear. Its first test returned a raw GraphQL error, because the required labels sat below the fold with no required marker.

Then a provider error

The runner forces tool_choice, which Claude 5.5 models reject, yet the picker offers them. The fix, found by guessing: turn off "Enable Function Calling." A trial user would conclude evals don't work.

Then it worked, and taught me something

The backfill: 24 GROUNDED, 8 UNGROUNDED. Every UNGROUNDED verdict had the same shape. The summary stated something the agent had verified with a tool, and the judge, seeing only the output, called it unsupported.

Right about its inputs. Wrong about the agent.

I tested the fix instead of asserting it

My proposal claimed that the trajectory would fix this. So I tested it: 32 traces exported from AX, each re-judged on the output alone and again with the agent's task, rules and tool calls.

Output alone, a strict judge passed 2 of 32. AX's lenient template had passed 24. Without the trajectory, the verdict tracked the prompt, not the agent.

With the trajectory, 26 of 32

Five of the eight UNGROUNDED verdicts flipped to GROUNDED. Three reviews AX's judge had passed were now flagged, each citing the line the summary contradicted. On my reading, all three flags are right.

Development workflow

Prompt v1 vs v2, scored in AX

From the first traced batch I wrote prompt v2 with two new rules, including "a new top-level folder is itself an index entry." Then I ran both prompts over all 70 labeled PRs as AX experiments, scored by five code evaluators and one judge.

v2 fixed the case it was written for and broke three others. The rule taught the model that only root-level folders count. I'm keeping v1 and scoping the rule tighter. Without the experiment, I'd have shipped v2 on one fixed example.

The failure that looked like success

My first attempt ran out of API credits after 16 rows. My task returned the error instead of raising it, so AX marked all 70 runs COMPLETED and scored 54 identical error strings.

That bug was mine. But one "these outputs look like errors" nudge would have caught it.

Every rough edge, ranked by how much it would hurt a real team

1 = shrug. 5 = a team on a trial stops here. Each item was logged with a date, and most have a screenshot.

What stands out is where the high scores cluster. The tracing issues scored 2s and 3s. The path from traces to a score I trust scored 4s and 5s. Four of the top six sit between "traces are flowing" and "I have an eval I believe."

Chapter VII

Agent evals that work on day one

The proposal

Make the first useful eval on an agent project take under five minutes, with no provider key and no plan upgrade, and put the trajectory in front of the judge before the user has to ask.

The problem, plainly

Tracing proves its value on day one. Evals don't. Between "traces are flowing" and "a score I trust" sit four gates, and I hit all four in one afternoon.

The public record agrees

Across 1,960 public developer posts I coded, agent testing and eval authoring are the second and third largest themes outside GitHub. LangSmith and Braintrust put code evaluators on their free tiers.

A · AGENT HEALTH PACK

Free, deterministic, offered automatically

On agent projects, Add Eval offers six built-in checks that need no model: completed, tool_budget, tool_loop, truncated_output, error_in_trace, latency_outlier.

Pure functions over attributes the instrumentors already emit. Exactly what I wrote by hand. Free on every plan.

Detect agents by shape, not by label

An agent is a root span with a TOOL descendant and more than one LLM descendant. Most instrumentors label the orchestrator CHAIN, not AGENT, so keying on span kind would miss most LangGraph and ADK agents.

B · TRAJECTORY FIRST

Offer the judge what the agent saw

From an agent project, lead with trace scope and a {trajectory} variable: tool calls in order, with arguments, truncated results and status.

Offered, not defaulted. It waits for trace completion and costs several times the tokens, so the estimate is shown first.

C · PRE-FLIGHT

Run it on three real spans before Save

Validate required fields inline. Translate provider errors into plain language, with the fix attached. Stop forcing tool choice on models that reject it.

Quick win alongside: a default price table, so Cost stops reading "--."

Nothing new in the data path

The detector is a shape query. The pack reads existing attributes. The digest is a rendering policy. Results land as ordinary eval columns, so Signal, monitors and Alyx see them unchanged.

One new output: each verdict can also go out as a webhook event, ready for the parent platform's workflows.

How I'd take it to engineering

  1. Start with three repros, independent of the bet. Forced tool_choice on 5.5 models, the dot-in-eval-name error that blames span matching, and the Cost tab setting a time range the plan can't serve. Each is a small change with a clear test, and each removes a moment where a trial ends.
  2. Pre-flight, one sprint. It reuses the existing "Test Evaluator On Spans" call. What changes is the order (pre-flight before Save), client-side validation, and a table that maps errors to suggested fixes.
  3. The pack, two sprints. Six pure functions, one UI card. The eval-column plumbing already exists. The detector can run lazily when Add Eval opens before we commit to running it on ingest.
  4. Trajectory last. It touches template variable resolution, trace-completion timing and the Add Eval entry point. Before designing it I'd ask the team two questions: how the online pipeline decides a trace is complete, and what the median judge input size is today.
  5. Plan gating is a funnel argument. The pack is free on every plan. Deterministic checks are what keep people around long enough to buy judges, Signal and seats. Gating them gates the funnel.

Counterweight: if the pack lifts eval adoption but judge usage falls, the free tier is cannibalizing instead of feeding the funnel. Watch both.

Who else is here

No competitor I checked offers a free, prebuilt, no-LLM health pack for agents. Grafana's Agent Observability, generally available since July, already scores multi-step turns and whole conversations with LLM judges, so trajectory-aware judging alone isn't a moat. What would set AX apart is the combination: free deterministic checks that every agent gets on day one, trajectory-aware judging, and verdicts that flow into the parent platform's workflows.

Grafana evaluation docs · GA note

What I'm not proposing

A new eval DSL. A replacement for Code Evaluators on Enterprise, which stay the path for custom checks. Changes to Signal or Alyx. The pack is deliberately boring: six checks that hold for every tool-using agent.

Limits of this evidence

One user, one free-tier account, one agent, one week. The judge findings come from 32 spans. The voice-of-customer data is public discussion and over-represents developers who post. 81% of it comes from GitHub, and enterprise buyers barely appear. What the evidence does support is the shape of the on-ramp problem and the specific failures, each of which I can reproduce.

Where AI coding tools helped

I built the agent, the tracing and the experiment harness with Claude Code. It helped most with work that had clear specs: the deterministic verifier, the dataset labeler, and moving the experiments onto a different runtime when my API credits ran out. It also drove the AX UI in a browser while I watched, which is how the builder failures got captured with screenshots in the order they happened. It helped least with the SDK's newer surfaces. The docs it knew were out of date, so it had to introspect function signatures, and the eval-naming rule isn't documented anywhere a model would think to look. The judgments in this piece, and any mistakes, are mine.

Method

Historical dates come from company announcements, registries (PyPI, GitHub) and regulator texts, and each was checked against a primary source where one exists. Fiddler's and Arthur's founding dates rest on press coverage. Predictions come from a forecast written in October 2026 that tags each claim as measured, vendor, analyst or press, then ran a separate adversarial review that downgraded three of its seven High-confidence cards. The take-home evidence comes from a dated log kept while working; nothing in it was edited afterward except typos.
